你正在为一组 skill 做**原子能力分解**。

每个 skill 的 capability_candidates 实际上是由若干**原子操作**组合而成的。
你的任务：把每个 skill 的 candidates 拆解成原子操作的集合。**所有 skill 共用同一个
canonical 命名空间**——同一个原子在不同 skill 里必须共享同一个 id。

⚠️ 这一步**不是**找差异，**不是**把 candidate 按"任务"聚类。
   把组合 candidate 拆开看，里面相同的子操作必须落到**同一个 id** 上。

============================================================
本次评测的 taxonomy（由 stage 0 提出，作为这次跑的强约束）
============================================================

domain：$domain

允许使用的 kind（**这一批 skill 必须只在这几类里挑**，不许新增、不许大小写变化）：

$kinds_block

modality 命名空间：

$modality_block

id 格式：$id_format

few-shot 范例（直接来自本批 skill，参考其粒度和命名风格）：

$few_shot_block

$notes_block
============================================================
canonical id 规则
============================================================

- 严格按 `id_format` 拼写。kind 部分是上面 kinds 里某个 name 的小写。
- modality 部分用 `modality_namespace.examples` 列出的形态；
  - 当 `modality_namespace.open == true` 且 examples 不够覆盖时，可以新增（保持
    convention）；
  - 当 `open == false` 时**不许**自造 modality，必须从 examples 里选。
- qualifier 只有"否则会冲突"才加（如 native-text vs scanned）。

⚠️ **同一概念必须用同一 id**：
  - skill A 出的 cap-read-pdf 和 skill B 出的 cap-read-pdf 是同一列。
  - 不允许 cap-read-pdf 和 cap-extract-pdf-text 都列出去而它们意义其实一样。

============================================================
分解规则
============================================================

1. **覆盖性**：candidate 里描述的每个独立动作（读、写、转换、推理、保留、对比……）
   都必须有对应的原子。如果一个 candidate 提到"保持样式"或"保留格式"，按 taxonomy
   里允许的 kind 找最贴近的那一类（一般是 PRESERVE 类——若 taxonomy 没有这类则
   忽略，不要硬塞）。

2. **去重**：一个 skill 内同 id 的原子只列一次。
   skill 有 csv→json、csv→xlsx、csv→html 三个 candidate，→ 该 skill 列一次
   读 csv 的原子，再加各写 json/xlsx/html 的原子各一次。

3. **不要造原子**：
   - 不要把 skill 描述里没有的能力填进去（不许"补齐"）。
   - 不要把语义不同的动作合到同一个 kind（taxonomy 里 kind 之间是互斥的）。

4. **每个 skill 的 atoms 不能为空。**

============================================================
输出格式（只输出 JSON，禁止围栏与说明）
============================================================

{
  "per_skill_atoms": [
    {
      "skill_id": "<exact skill_id from input>",
      "atoms": [
        {
          "id": "<按 id_format 拼写>",
          "kind": "<必须是 taxonomy.kinds 中某个 name>",
          "name": "<人类可读短名>",
          "description": "<这个能力本身做什么；不要提 skill_id>",
          "input_shape": "<输入的形态——什么文件 / 数据结构>",
          "output_shape": "<输出的形态>",
          "judgement_dimensions": ["<判分维度1>", "<判分维度2>"]
        }
      ]
    }
  ]
}

============================================================
硬性规则
============================================================

- 每个 skill_id 必须是输入 skills_payload 里出现过的 id，不许编造、不许省略前缀版本号。
- 每个 atom 必须填全 id / kind / name / description / input_shape / output_shape /
  judgement_dimensions（≥1 项）。
- atom.kind **必须**是上面 taxonomy.kinds 中某个 name（大写）。其他值会被拒绝。
- description / input_shape / output_shape **不能出现任何 skill_id** —— 它们描述能力本身。
- 同一 skill 内 id 不重复；跨 skill 同 id 意义必须一致（kind / 描述对得上）。
- 不输出 skill_capability_map（下游会从 skill_id 反推，逐 atom 合并）。
- 不输出多余字段。
