你正在为一组 skill 做**原子能力分解**。

每个 skill 的 capability_candidates 实际上是由若干**原子操作**组合而成的。
例如 "translate PDF" 这一条 candidate，本质上 = 读 PDF + 翻译文本 + 写 PDF + 保持样式
四个原子的组合。"convert CSV to JSON" = 读 CSV + 转换表格语义 + 写 JSON。

你的任务：把每个 skill 的 candidates 拆解成原子操作的集合。**所有 skill 共用同一个
canonical 命名空间**——同一个原子在不同 skill 里必须共享同一个 id。

⚠️ 这一步**不是**找差异，**不是**把 candidate 按"任务"聚类（比如把"翻译"和"转换"
当成两列）。把"翻译"拆开看，里面的"读 PDF"和"读 PDF 文本"做转换的"读 PDF" 是
**同一个原子**——它们必须落到同一个 id 上。

============================================================
原子分类（kind）
============================================================

- READ       从某种格式读取（只输入→中间表示，不变换，不写）
- WRITE      把内容写入某种格式（中间表示→输出，不变换语义）
- TRANSFORM  在两种格式 / schema 之间做结构性转换（如表格→JSON，含字段映射）
- EXTRACT    从混合内容中抽取子结构（表、字段、章节、元数据）
- INFER      用模型 / 规则推理产生**输入里不直接存在**的内容（翻译、摘要、分类、问答）
- PRESERVE   保持源文档的某种属性（样式、布局、字体、元数据）
- COMPARE    对比多个文档 / 数据集，产出差异
- COMPOSE    把多个输入合成一个输出（合并、拼接、批处理）
- VALIDATE   校验 / 检查结构合规性

每个原子**只能有一个 kind**。

============================================================
canonical id 规则
============================================================

格式： cap-<kind>-<primary_modality>[-<qualifier>]

  kind             小写：read / write / transform / extract / infer / preserve / compare / compose / validate
  primary_modality 小写： pdf / docx / xlsx / csv / json / markdown / html / png / jpg / txt / pptx /
                          image / tabular / text / multi-document
  qualifier        可选；只有"否则会冲突"才加（如 cap-read-pdf-native-text vs cap-read-pdf-scanned）

特殊场景：
  - INFER 用任务名做 modality：cap-infer-translation, cap-infer-summary, cap-infer-classification
  - PRESERVE 用属性做 modality：cap-preserve-style-docx, cap-preserve-layout-pdf
  - TRANSFORM 用 source-target：cap-transform-tabular-to-json
  - COMPARE 用对象类型：cap-compare-documents
  - COMPOSE 用产物：cap-compose-pdf-from-images

⚠️ **同一概念必须用同一 id**：
  -  skill A "translate DOCX" 拆出 cap-read-docx, cap-infer-translation, cap-write-docx, cap-preserve-style-docx
  -  skill B "convert DOCX to Markdown" 拆出 cap-read-docx (**与 A 共享！**), cap-transform-docx-to-markdown, cap-write-markdown
  -  不允许 cap-read-docx 和 cap-extract-docx-text 都列出去而它们意义其实一样。

============================================================
分解规则
============================================================

1. **覆盖性**：candidate 的 actions 列表（READ/WRITE/TRANSFORM/INFER 等）里出现的每个动作，
   都必须能在该 skill 的原子里找到对应。
   - 如果一个 candidate actions 是 [READ, TRANSFORM, WRITE]，至少要分出一个 READ 类原子、
     一个 WRITE 类原子、一个 TRANSFORM/EXTRACT/INFER 类原子。
   - 如果 candidate 描述里提到"保持样式"、"保留格式"，要单独出一个 PRESERVE 原子。

2. **去重**：一个 skill 内同 id 的原子只列一次。
   skill 有 csv→json、csv→xlsx、csv→html 三个 candidate，→ 该 skill 列一次 cap-read-csv，
   再加 cap-write-json、cap-write-xlsx、cap-write-html 各一次。

3. **不要造原子**：
   - 不要把 skill 描述里没有的能力填进去（不许"补齐"）。
   - 不要把 INFER 和 TRANSFORM 混淆——单纯字段重命名是 TRANSFORM；自然语言翻译是 INFER。

4. **每个 skill 的 atoms 不能为空。**

============================================================
输出格式（只输出 JSON，禁止围栏与说明）
============================================================

{
  "per_skill_atoms": [
    {
      "skill_id": "<exact skill_id from input>",
      "atoms": [
        {
          "id": "cap-read-pdf",
          "kind": "READ",
          "name": "Read PDF",
          "description": "Extract reading-order text and structure from a PDF file.",
          "input_shape": "A .pdf file (with embedded text or scanned).",
          "output_shape": "Text content or structured representation of the PDF.",
          "judgement_dimensions": ["correctness", "completeness", "reading_order"]
        },
        {
          "id": "cap-infer-translation",
          "kind": "INFER",
          "name": "Translate text",
          "description": "Translate natural-language text from one language to another while preserving meaning.",
          "input_shape": "A piece of natural-language text in the source language.",
          "output_shape": "The same text translated to the target language.",
          "judgement_dimensions": ["semantic_fidelity", "fluency", "terminology"]
        }
      ]
    }
  ]
}

============================================================
硬性规则
============================================================

- 每个 skill_id 必须是输入 skills_payload 里出现过的 id，不许编造、不许省略前缀版本号。
- 每个 atom 必须填全 id / kind / name / description / input_shape / output_shape /
  judgement_dimensions（≥1 项）。
- description / input_shape / output_shape **不能出现任何 skill_id** —— 它们描述能力本身。
- 同一 skill 内 id 不重复；跨 skill 同 id 意义必须一致。
- 不输出 skill_capability_map（下游会从 skill_id 反推，逐 atom 合并）。
- 不输出多余字段。

输入

用户 query：
$query
