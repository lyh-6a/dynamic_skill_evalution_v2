你正在审阅一组**已经做过原子分解**的 capability 列表，目标是**找出语义重复**的列
并把它们合并成一组 canonical id。

============================================================
背景
============================================================

上游已经按 stage 0 提出的 taxonomy 把每个 skill 的 capability_candidates 拆成了
原子操作，并按 id 求并集合并过一次。但是不同 skill 在 stage-1 的命名仍然有出入，
比如笼统的 cap-read-document 和具体的 cap-read-pdf 同时出现。

⚠️ 这一步**不**是再次聚类、**不**重新分类，**不**改 kind。
只做一件事：当两个/多个原子描述同一件事时，挑一个最具体、信息量最大的 id 作为
canonical，其它 id 都变成它的别名（absorbs）。

============================================================
本次评测的 taxonomy（同 stage 1）
============================================================

domain：$domain

允许的 kind（与 stage 1 完全一致）：

$kinds_block

$notes_block
============================================================
合并判定规则
============================================================

合并 A → 当且仅当所有以下条件**全部满足**：
  1. **kind 完全一样**（cross-kind 合并永远不允许）。
  2. input_shape 在概念上等价或一方更具体（例如 generic "document" 包含
     specific "pdf"）。
  3. output_shape 在概念上等价或一方更具体。
  4. description 描述的是同一件事，不是相似但不同的事。

合并选 canonical 的优先级：
  - 更具体 > 更笼统。 cap-read-pdf 优先于 cap-read-document。
  - 更具体 > 更具体。 含 qualifier 的 id 优先于不含的（仅当其他 id 是它的真子集）。
  - 一对多场景（cap-read-document 可以拆到 cap-read-pdf, cap-read-docx,
    cap-read-xlsx）：把笼统 id 变成 canonical 列表（expand 模式，下面输出格式有说明）。

⚠️ **不要为了减少列数硬合并**：
  - 不同 modality 的写出能力是两件事，不要合到一个 cap-write-<umbrella>。
  - 不同任务类型的 INFER（如翻译 vs 摘要 vs 分类）完全不是一回事。
  - 同一 kind 下不同 modality 也不要硬合。

⚠️ **保守优先**：拿不准就不合，留两条独立列比错误合并更好。

============================================================
输出格式（只输出 JSON，禁止围栏与说明）
============================================================

两种合并模式：

模式 1 —— 单 canonical 吸收：
{
  "canonical_id": "<更具体的 id>",
  "absorbs": ["<更笼统的 id>"],
  "mode": "absorb",
  "rationale": "<一句话解释为什么这两条是同一件事>"
}

模式 2 —— 笼统 id 拆到多个 specific：
{
  "canonical_id": null,
  "absorbs": ["<笼统的 id>"],
  "mode": "expand",
  "expand_to": ["<具体 id 1>", "<具体 id 2>", "<具体 id 3>"],
  "rationale": "<一句话解释笼统 id 实际覆盖了哪几个 specific>"
}

  - mode=absorb：absorbs 中所有 id 的 skill_ids 全部并到 canonical_id 上，absorbs 列被删除。
  - mode=expand：absorbs 中每个 id 的 skill_ids 复制到 expand_to 列出的每个目标列，原列删除。
    expand_to 中的每个目标 id **必须在输入 capabilities 列表中已经存在**（不许凭空造）。

整体输出：
{
  "merges": [ { ... }, { ... } ]
}

如果没有任何可合并的，输出 `{"merges": []}`。

============================================================
硬性规则
============================================================

- absorbs 中的每个 id **必须在输入 capabilities 中存在**。
- canonical_id（mode=absorb）和 expand_to 中的每个 id **必须在输入 capabilities 中存在**。
- 同一个 absorbs id 不能在多个 merges 里都出现（一次性消耗）。
- 一个 canonical_id 可以在 mode=absorb 中出现多次（吸收多个别名）。
- mode=absorb 时，absorbs 不能包含 canonical_id 自己。
- 不允许跨 kind 合并。
